# Execution plan: R01, R02, R11 and R14

Date: 2026-09-26. Status: implemented and verified. See the [implementation report](../2026-09-26-p1-implementation/REPORT_EN.md) for tests, real acceptance, local rollout and remaining historical decisions.

This plan addresses the four P1 findings in the [latest audit](REPORT_EN.md): serving-resource ownership, delayed serving workers, incorrect reject/OTHER targets, and destructive source ingestion. Code, comments, schemas, tests, documentation and UI additions will be authored in English. User authentication remains deferred.

## Target behavior and design decisions

| Finding | Required outcome | Chosen approach |
| --- | --- | --- |
| R01 | Serve never overwrites or deletes a resource merely because its name matches | Immutable resources named for a ServingRun, explicit recorded ownership and UID checks |
| R02 | A delayed old worker cannot replace, route traffic to, or publish readiness over a newer revision | Per-run Services, database-selected prediction target, lease epochs and conditional publication; cleanup for delayed resources |
| R11 | A training target represents a class actually selected by an annotator | A versioned single-label choice workflow; no implicit OTHER target; explicit legacy compatibility |
| R14 | Reordering, retrying or shortening an import cannot change old record identities or remove source rows | Append-only managed sources, stable keys, transactional imports and durable receipts; conflicting edits rejected |

R01 and R02 form one serving change. R14 should land before the final R11 demonstration so that newly labeled examples have reliable source identities. Contract design for R11 can begin earlier. Existing PostgreSQL, Django, Kedro, Prodigy, FastAPI and React remain the implementation stack.

For R11, the recommended product decision is **one explicitly selected class per text**. Positive/negative sentiment fits this objective. `OTHER` is available only if explicitly configured as a real class and selected by the annotator. An uncertain or rejected item is not assigned a target. Multilabel classification and learned active-learning acquisition are separate work.

For R14, the initial correction policy is deliberately concrete: **existing source records are immutable**. A changed text under an existing source key/record key rejects the import. A revised corpus receives a new source namespace/version through an explicit source-creation action. General in-place editing and a full dataset-versioning platform are not prerequisites for this repair.

## Stage 1 — R01: explicit serving-resource ownership

### 1.1 Persist a complete serving resource plan

Extend ServingRun with a versioned resource plan containing trusted cluster/namespace identity, Deployment and Service names, recorded UIDs, an ownership marker/creation-intent token and the relevant desired-spec fingerprint. New names derive from the run UUID, for example `serve-<run UUID>` and `serve-svc-<run UUID>`; they are never derived from an editable model title.

Use an immutable per-run ConfigMap as an ownership anchor. Persist its identity before creating dependents. Deployment and Service owner references point to the anchor's exact UID in the same namespace. Store only bounded, non-secret identity/configuration metadata there; source texts and database credentials do not belong in the anchor.

Add named constraints for valid layout/state values and resource-name uniqueness for the new layout. Preserve old rows as an explicit `legacy-fixed-v1` layout; do not invent missing UIDs or change historical names in a data migration.

### 1.2 Replace unrestricted replacement with create-or-observe

Remove the normal `_put` behavior that reads an arbitrary existing object and replaces it using its current UID/resourceVersion.

| Observed resource | Controller behavior |
| --- | --- |
| Absent; run still authorized to start | Create the immutable intended resource |
| Present; recorded UID and ownership/spec match | Observe it without rewriting its selector or template |
| Present; UID missing locally because create succeeded before a crash | Recover only when it matches the durable creation intent, exact anchor identity and expected application-owned specification |
| Present; foreign owner, conflicting intent, or changed recorded UID | Return an identity conflict; do not patch, replace or delete |
| Previously recorded object is now absent | Report loss; require Stop/new Serve rather than silently adopting a replacement |

Define the spec fingerprint over fields the application owns, excluding server-assigned status, resourceVersion, IPs and defaulted metadata. A matching name or a single ownership label is insufficient. An ambiguous anchor itself requires review instead of speculative adoption.

### 1.3 Carry identity through every consumer

Update manifest generation, service health checks, local port-forward targets, in-cluster DNS selection, Stop, deletion preview/execution and resource inventory to use the saved plan. Remove new-run assumptions that names always contain `model_id`.

Inventory **all relevant serving runs** when deleting a model, not only `current_serving`; otherwise a failed/older run's resources can escape cleanup. Keep model PVC ownership separate: stopping a serving run must not delete shared training artifacts.

Deletion continues to use UID preconditions. Server-returned UIDs are recorded with an ownership-checked conditional database write. If that write loses ownership, the controller must not publish readiness; recovery observes the existing intended object safely.

### 1.4 Required tests and completion condition

- Pre-existing foreign Deployment, Service and anchor remain byte-for-byte unchanged.
- A same-name replacement with a different UID is refused even when its labels look correct.
- Retry after successful create/lost database acknowledgment observes the same object and does not create a second intent.
- A changed desired template/selector is reported as a conflict, not silently replaced.
- Stop removes only the recorded run's resources; a neighboring model and its PVC remain unchanged.
- New resources contain the expected namespace, run identity and owner references.

**R01 is complete when no normal Serve/Stop/Delete path can take ownership from a matching name alone, and this is demonstrated against real Kubernetes objects.**

## Stage 2 — R02: isolate revisions and reject late publication

### 2.1 Remove mutable shared prediction routing for new runs

The public prediction URL remains `/api/models/{id}/predict/`. Django resolves that model's current READY ServingRun, then calls **that run's Service**. New runs do not rewrite `serve-svc-{model_id}` or a shared alias. Local port forwarding follows the same saved Service identity.

The response must match the expected serving run, training run and class contract. After the response arrives, recheck that the same run is still current and eligible; a request spanning Stop or a version switch returns a retryable changed-version response instead of presenting obsolete output as current.

This is the principal external isolation boundary: an old controller can at most act on names unique to its old run. It cannot read a newer shared Service resourceVersion and overwrite that route. Kubernetes resourceVersion prevents conflicting updates to a particular object; it does not by itself express the application's current serving intent. [Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/#resource-versions).

### 2.2 Make lease ownership explicit at publication

Add a monotonically increasing lease epoch per run, or an equivalent durable generation with the same semantics. Every lease acquisition and Stop invalidation changes the generation.

Starting/observing a serving revision requires all of:

1. Matching owner and lease epoch.
2. An unexpired lease, using consistent database time semantics.
3. A legal run state.
4. The expected `current_serving` pointer.
5. No applicable model/dataset cleanup reservation or retirement.

Use a documented database lock order consistent with the current domain: dataset, model, operation row where all are needed. Keep Kubernetes and HTTP calls outside those transactions. Conditional progress, UID, error, readiness and lease-release writes all include the relevant generation/state conditions; a late failure must not overwrite a newer success either.

Stop first invalidates prediction eligibility and stale-owner publication in the database, then performs external cleanup. Cleanup authorization is distinct from activation authorization: cleaning a terminated old run must not require that it remain the model's current run, nor clear a newer run's state.

### 2.3 Cover creates that arrive after Stop

Do not claim that a database check cancels an already in-flight Kubernetes request. Retain run tombstones and reconcile explicitly owned terminal-run leftovers. Use UID-bound owner references as an additional collection mechanism. Kubernetes garbage collection is asynchronous, and dependents can race with deletion; inspect actual resource/Pod absence instead of assuming the delete response is completion. [Kubernetes garbage collection](https://kubernetes.io/docs/concepts/architecture/garbage-collection/).

The resulting guarantees are:

- After Stop, the old run cannot become an eligible prediction target again.
- A new run's resources and database state are unaffected by delayed old work.
- A late-created old resource is eventually collected while the control plane/reconciler is available; it is not forgotten because its run is already STOPPED.
- Ambiguous ownership becomes a visible review condition, never a reason to delete an unrelated object.

Terminal resource collection must be bounded and must discover only resources tied to saved application intents. Do not broaden this into automatic deletion of historical `serve-*` resources.

### 2.4 Race matrix

Use barriers/event traces and an injectable clock. Avoid fixed sleeps as the proof of correctness.

| Interleaving | Required final observation |
| --- | --- |
| A passes ownership check → A pauses → lease expires → Stop A → start B → resume A | B's UID, spec, Service selection and database pointer are unchanged |
| A finishes HTTP readiness after Stop | A cannot publish READY or rewrite startup outcome |
| Owner B acquires the same run after A expires → A releases its old lease | B retains its lease and generation |
| Deployment create succeeds → controller dies before recording UID | A new owner recovers exactly that intended object |
| Stop completes an absence check → delayed create for the old run arrives | It receives no application traffic and is eventually collected |
| Old cleanup resumes after a newer run starts | Only old recorded resources are removed |
| Prediction starts on A → Stop/version change occurs → A response arrives | Response is rejected as obsolete; no class/revision mismatch is shown |

Run database races on real PostgreSQL and external identity/deletion tests on a disposable Kubernetes namespace. Mock-only success is insufficient to close R02.

## Stage 3 — R14: stable, transactional source ingestion

### 3.1 Define minimal managed source tables

Use a small managed source model, with final names adapted to the repository conventions:

| Entity | Required fields and constraints |
| --- | --- |
| SourceCollection | Stable UUID, unique operator-approved source key, immutable identity-policy version |
| SourceRecord | Stable UUID primary key; protected source FK; external record key; exact text and required provenance; content digest; `UNIQUE(source_id, external_key)` |
| SourceImportReceipt | Import UUID; source FK; request key; canonical input fingerprint; parser/identity-policy version; inserted/unchanged/input counts; committed timestamp; unique request identity per source |

Use explicit migrations/setup DDL owned by the schema role, not implicit table creation from Pandas. Keep the tables in a managed schema with deliberate grants. All public/CLI identifiers and timestamps must have defined types and length limits.

### 3.2 Define record identity before conversion

Replace `reset_index()` as the source of semantic IDs.

- Default mode requires a real upstream ID, preserved as a string. `001` must not silently become `1`.
- Files without IDs may use an explicitly selected content-addressed mode, keyed by source namespace plus exact text and agreed semantic metadata. Persist that mode/version; do not silently select it based on missing input.
- In content-addressed mode, identical occurrences cannot be distinguished without another upstream identifier. Reject duplicate identities by default; an explicit deduplication option must report its count and behavior.
- Specify canonical encoding and metadata fields for hashing. Do not trim, lowercase or normalize user text merely to manufacture a match.
- Same key and same content means unchanged. Same key and different text/provenance means a conflict. Missing keys in a later import do not imply deletion.

Keep the `source` display/provenance value distinct from the registered source namespace used for identity.

### 3.3 Use an explicit import transaction

1. Parse and validate input with configured file/row/text limits and structured diagnostics.
2. Compute an order-independent fingerprint that includes the parser and identity policy and accounts for duplicate multiplicity.
3. Provide a read-only dry run: inserted, unchanged, duplicate/conflicting counts and bounded identifying diagnostics. Avoid printing full text or credentials into routine logs.
4. Begin a bounded PostgreSQL transaction; acquire a transaction-scoped advisory lock using a documented, stable source-derived key to serialize imports into that source. Every importer uses the same key scheme. Hash collisions may serialize unrelated imports but must never alter record identity. This avoids granting UPDATE merely to take a row lock on otherwise immutable source metadata.
5. Recheck request-key replay. Same key/same fingerprint returns the committed receipt; same key/different input is a conflict.
6. Load validated records into temporary staging and validate uniqueness, required values and existing-record content consistency again inside the transaction. A dry run is advisory, not a stale authorization to overwrite.
7. Insert genuinely new records with bound values and quoted approved identifiers. Do not use `ON CONFLICT DO UPDATE` to change existing source text.
8. Write the committed receipt in the **same transaction** as source insertion. On any failure, no partial source publication or success receipt remains.
9. Return the receipt and counts. After an ambiguous connection failure at commit, retry by the same request key to discover the committed outcome.

This gives replay safety without a new background ingestion platform. Empty or malformed input is rejected; it never empties an existing source.

### 3.4 Integrate the Kedro pipeline and reader

Remove the `SQLTableDataset` output configured with `if_exists: replace`. Have the explicit ingestion adapter/node perform the transaction and produce an import receipt, rather than returning a DataFrame whose later save drops/recreates a table. Preserve stable identity columns through JSONL/CSV conversion without Pandas numeric coercion.

Remove destructive ingestion from the aggregate default Kedro pipeline: a generic `kedro run` must not replace or import source data implicitly. Approved training/annotation pipelines continue to use explicit pipeline names.

Extend the trusted source registry and read adapter to select a specific managed source namespace. Emit source identity, record identity, content digest and contract version into annotation metadata. Freeze a dataset's source identity once it has annotation history; changing the source requires a new binding/version. This narrow adjacent guard is necessary so a source change cannot reintroduce R14 through overlapping IDs (the mechanism reported as R15).

Retain parameterized SQL and the existing server-owned allowlist. API payloads do not gain arbitrary table/schema access.

### 3.5 Enforce source immutability with privileges

The ingest runtime receives the necessary SELECT/INSERT rights on managed source records and receipt tables, with no UPDATE/DELETE/TRUNCATE/DROP or schema-creation rights. The setup/migration role owns schema objects. The reader retains SELECT-only access, and the application does not acquire source-write privileges.

The existing ingest role owns `all_data`; revoking ordinary DML grants alone cannot remove an owner's ability to alter/drop its table. The cutover therefore includes an explicit reviewed ownership/grant migration, separate from the helper that rotates all service passwords. No password rotation is required merely to implement this design. [PostgreSQL privileges](https://www.postgresql.org/docs/current/ddl-priv.html).

### 3.6 Legacy source treatment

Preserve the existing `all_data` contents and IDs. Keep it as a read-only legacy source during the transition. New imports use managed source namespaces.

Prepare a read-only import/adoption preview for historical rows. Do not infer stable identity from current row order or pretend that the old positional IDs were reliable upstream IDs. Any subsequent historical copy records original source/ID provenance and keeps old annotations bound to their original identities until a deliberate migration is selected.

### 3.7 Required data tests

- Import A, reorder A, retry A: stable record UUIDs and contents; no duplicates.
- Import a subset of A: missing rows remain present and unchanged.
- Import A plus new rows: only new records are inserted.
- Same key with changed text: the whole import fails, including any new rows in that batch.
- Duplicate keys with identical and conflicting contents: defined rejection/deduplication behavior and accurate counts.
- Unicode, quotes, literal SQL-looking values, leading-zero IDs, null/missing IDs and empty files are handled explicitly.
- Two overlapping concurrent imports: one valid serial outcome, no lost update or duplicate identity.
- Crash/connection loss before commit and after commit acknowledgment loss: rollback or same-receipt recovery.
- Runtime ingest credentials cannot modify/delete old records or drop tables, even with direct SQL outside the normal importer.
- Annotation exclusion matches source plus stable record identity; overlapping IDs in different sources cannot suppress each other.

**R14 is complete when an import cannot change an existing source record's identity/content or remove absent rows, through either the normal pipeline or its runtime database privileges.**

## Stage 4 — R11: explicit labels and a versioned classification contract

### 4.1 Introduce the new annotation policy

Add a policy such as `single-label-choice-v2` for new datasets. It is immutable after annotation begins and is included in launch snapshots. New annotations show all configured classes and require exactly one selected class on acceptance. For this mode require at least two explicit classes; a one-label binary task needs a separate, explicitly defined objective.

The installed Prodigy recipe supports exclusive choice and validates accepted selections. Use its supported behavior through an approved recipe/adapter while preserving the project's source metadata and identity/hash policy. The official text-classification documentation also distinguishes exclusive choice from independent binary decisions. [Prodigy text classification](https://prodi.gy/docs/text-classification).

Do not blindly enable text-only deduplication that would discard distinct source records. Test how the installed loader/recipe calculates input/task hashes and excludes completed items. Stable source identity and the intended deduplication unit must survive this boundary.

Update the server-owned recipe allowlist and entry points; do not reopen arbitrary recipe commands. The existing dummy-model recipe remains clearly marked legacy. The new manual workflow makes no active-learning claim.

### 4.2 Centralize conversion rules in the shared contract package

| Stored answer under the new policy | Training behavior |
| --- | --- |
| Accept with exactly one allowed class | Use that explicit class |
| Accept with no class, multiple classes, an unknown class, or malformed content | Reject as invalid with a specific preflight error |
| Ignore/skip | No training target; count as skipped |
| Reject | No inferred class; exclude/count as needing review |
| Explicitly selected configured OTHER class | Use OTHER as an ordinary explicit class |
| Legacy binary reject | Requires legacy-policy review; never auto-convert to OTHER or to the opposite class |

Use one pure normalization/conversion implementation from `kedrogy_contracts` in Django preflight and the Kedro training job. Count accepted, skipped, rejected, invalid and conflicting examples separately. Validate usable data and class support before starting Kubernetes training, and recheck the same fingerprint at execution.

Bind fingerprints to policy version, ordered class schema, annotation content and source provenance. A source/policy/schema change is not the same training input. Do not silently mix incompatible annotation policies in one run.

### 4.3 Carry class schema through training, artifacts and prediction

The existing code assumes `[OTHER, ...labels]` in several places. Change all consumers coherently:

1. Dataset/model API and saved training snapshot.
2. Preflight, annotation summary and Kedro conversion.
3. Hugging Face `num_labels`, `id2label` and `label2id`.
4. Checkpoint manifest/verification receipt and server-side receipt validation.
5. Serving snapshot and inference startup verification.
6. Prediction response contract and Django response validation.
7. React runtime parsers and display; legacy HTML result rendering.

For v2, class IDs are `0..N-1` in the explicitly stored order. Class zero is the first actual class, not an automatically inserted OTHER. Preserve bounded receipt sizes; configurations too large for the protocol must fail clearly before training rather than at checkpoint publication.

Do not equate artifact-format version, annotation-conversion policy and HTTP protocol version. Define a compatibility matrix and validate their combinations. An unknown version/mapping must fail closed with a readable compatibility error.

### 4.4 Preserve verified legacy models without falsifying their meaning

The new readers support known v1 and v2 artifacts. Known v1 checkpoints retain their existing `[OTHER, ...labels]` mapping and are visibly identified as legacy policy; their classifier weights and class IDs are not rewritten. Unverified/invalid artifacts remain unverified/invalid.

Disable new default training under `reject-other-v1`. A legacy annotation dataset requiring interpretation returns a policy-review error with safe counts and next steps. Prepare a read-only conversion preview: which accepted labels can be retained exactly, which records conflict, and which rejects require reannotation. Applying a selected migration writes a new annotation set/binding with provenance; it does not edit historical answers in place.

The working P/N versus positive/negative mapping is not inferred by this plan. Implementation can finish and demonstrate the corrected workflow using new synthetic v2 data while that historical choice remains explicit.

### 4.5 Required contract and workflow tests

- A positive text with a rejected negative suggestion never creates an OTHER/negative target.
- Exactly one selected positive/negative label produces the matching class ID under v2.
- Reject, ignore, empty choice, multiple choice and unknown labels follow the table above.
- Explicit OTHER behaves as a normal configured class; implicit OTHER is absent.
- Conflicting accepted answers for the same source record are surfaced for review.
- API preflight and training produce identical normalized examples/counts/fingerprints.
- Changing the ordered class schema or policy changes the fingerprint and invalidates stale preflight.
- A real tiny v2 checkpoint trains, publishes, verifies and predicts with the same mapping across all consumers.
- A verified v1 checkpoint still predicts its original class-zero OTHER correctly; a v1/v2 mix-up is rejected.
- A real browser annotation answer reaches the database with the expected source metadata and selected class, then passes the same training contract.

**R11 is complete when new default training cannot manufacture a target from a rejected suggestion, and both new and legacy checkpoint mappings are correctly enforced end to end.**

## Migration, rollout and rollback

Use an expand-and-enable sequence:

1. Add nullable/versioned schema fields and new managed source tables. Existing rows keep their old semantics. Verify migrations on populated synthetic PostgreSQL records and test rollback before new-format writes exist.
2. Build backend/ML/frontend images capable of reading the old and new contracts. Verify the changed modules are present in the images, then pin their digests. Update approved image aliases coherently.
3. Pause new lifecycle submissions during the controller cutover and inspect the actual process tree. Stop all old queue workers/reconcilers, including the child that the current local supervisor can leave behind. Merely changing the API process does not prevent old code from continuing Kubernetes writes.
4. Establish the new controller exclusively, enable per-run serving resources, and verify behavior with a synthetic model. Previously created fixed-name resources remain in the explicit legacy inventory; new code does not silently adopt them.
5. Enable managed-source imports and apply the scoped ownership/privilege changes. Keep existing source/annotation bindings intact.
6. Enable v2 annotation/training only after backend, ML and frontend all support the mapping. Demonstrate the workflow on a new synthetic dataset before selecting any historical migration.

A runtime rollback after v2 records/artifacts exist must use a release that understands those records, or disable the affected operations and roll forward. Do not run an old controller against new resource plans or downgrade schemas by discarding source rows, mappings or receipts. No destructive reverse migration is claimed to be safe after new data is written.
